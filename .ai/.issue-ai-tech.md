# Техническое ТЗ: vv-db-connection

Нетехническая постановка — `.ai/.issue-ai.md`. Здесь — как это будет построено.

## 1. Стек и пакет

- TypeScript (`strict`, `target`/`module` = `ESNext`), ESM-пакет (`"type": "module"`), Node.js `>=18`.
- Сборка: `tsc && tsc-esm-fix --target=distjs`; публикуется только `distjs/src` (`main`/`types`/`exports["."]` → `distjs/src/index.{js,d.ts}`).
- Тесты: встроенный `node:test` через `tsx` (`node --import tsx --test test/*.test.ts`); дымовой тест `test:smoke` — сборка + импорт пакета и проверка экспорта `DbConnection`.
- Драйверы — **опциональные peerDependencies** (ставит потребитель только нужные): `mssql ^12.5.0`, `oracledb ^26.0.0`, `pg ^8.20.0`, `node-firebird 2.19.1` (точный пин — см. §7.4). В devDependencies — те же драйверы, `@types/*`, `tsx`, `tsc-esm-fix`, `typescript ^7.0.2` (решение владельца — не понижать).
- Лицензия MIT, репозиторий `github.com/VasilevVitalii/vv-db-connection`.
- Слой переносится из `src/db/` проекта gi-bridge поведение-сохраняющим рефакторингом.

## 3. Конфигурация подключения

`TConnectionParam = TConnMssql | TConnOra | TConnPg | TConnFb`, дискриминатор `kind`; `TDbKind = TConnectionParam['kind']` = `'mssql' | 'pg' | 'ora' | 'fb'`. Все `connectTimeout` — в миллисекундах.

Всегда `blobAsText: true`.

### 3.5. Валидация конфигурации (синхронно, `TypeError`)

- `assertTimeoutMs(label, ms)`: допустимо `undefined`, `0` или конечное число `>= 0`; иначе `TypeError("<label> must be a non-negative finite number of milliseconds, got <ms>")`. Вызывается в конструкторе `DbConnection` (для `connectTimeout`) и повторно в конструкторах адаптеров — двойная проверка осознанная (§8, решение 6).
- `assertOraPool(p)`: `poolMin` — целое `>=0`, `poolMax` — целое `>=1`, `poolIncrement` — целое `>=1`, `queueTimeout` — целое `>=0`, `poolMin <= poolMax`; сообщения `ora: <name> must be an integer >= N`, `ora: poolMin must not exceed poolMax`.

### 3.6. Описание подключения

- `dbTitle(c)`: `server|host:port [database|service]` с подстановкой дефолтного порта; для mssql без БД — `[default]`.
- `dbUser(c)`: имя пользователя; для mssql ntlm — `domain\user`.

## 4. Контракты (`db/types.ts`)

```ts
type TDbParam = { name: string; value?: unknown; type?: string; direction?: 'in' | 'out' | 'inout' }
type TDbCol   = { name: string; kind: string; len?: number; scale?: number; precision?: number }
type TDbRes   = { schema: TDbCol[]; rows: Record<string, unknown>[]; rowsAffected?: number; outParams?: Record<string, unknown> }

type TDbErrorKind = 'connect' | 'query' | 'tx' | 'user' | 'timeout' | 'aborted'
type TDbError = { message: string; code?: string; kind: TDbErrorKind; stack?: string }
type TResult<T, E = TDbError> = { ok: true; result: T } | { ok: false; error: E }

type TExecOptions = { signal?: AbortSignal; firstDataTimeoutMs?: number; idleTimeoutMs?: number }
type TTxOptions   = { timeoutMs?: number; signal?: AbortSignal }

type TDbStreamEvent =
  | { kind: 'schema'; schema: TDbCol[] }
  | { kind: 'row'; row: Record<string, unknown> }
  | { kind: 'rowsAffected'; count: number }
  | { kind: 'outParams'; params: Record<string, unknown> }
  | { kind: 'finish'; error?: TDbError }

type TDbTxResult = { rows: Record<string, unknown>[]; rowsAffected?: number; outParams?: Record<string, unknown>; implicitResults?: TDbRes[] }
type TDbTxExec   = (query: string, params: TDbParam[]) => Promise<TDbTxResult>
type TDbTxCb<T = void> = (exec: TDbTxExec, signal: AbortSignal) => Promise<T>

interface IDbAdapter {
  versionQuery(): string
  versionFallbackQuery?(): string
  pingQuery(): string
  execStream(query, params, callback: (e: TDbStreamEvent) => void, signal?: AbortSignal): Promise<void>
  execTxDynamic<T = void>(cb: TDbTxCb<T>, timeoutMs?: number, signal?: AbortSignal): Promise<TResult<T, TDbError>>
  close(): Promise<void>
}
```

Семантика полей:
- `TDbParam.type` — имя нативного типа драйвера; учитывается только mssql и ora; pg и fb выводят тип из JS-значения и `type` игнорируют. `direction: 'out' | 'inout'` — только Oracle (значение возвращается в `outParams`); остальные адаптеры отклоняют не-`in` направление ошибкой `<kind>: <direction> parameters are not supported`. Для `out` `value` можно опустить.
- `TDbCol.kind` — имя типа драйвера (не нормализуется между СУБД).
- `TDbRes.rowsAffected` — только для DML (в т.ч. `0`); у SELECT отсутствует.
- `TDbError.code` — код драйвера (SQLSTATE для pg, `ORA-xxxxx`/`NJS-xxxx` для ora, номер SQL Server для mssql, `gdscode` для fb) либо синтетический код библиотеки: `TIMEOUT`, `ABORTED`, `COMMIT_TIMEOUT`, `FB_CONN_LOST`, `NO_VERSION`. Различение ошибок — по `code`/`kind`, не по `message`.

Классы `kind`:

| kind | Когда |
|---|---|
| connect | не удалось открыть соединение / создать адаптер (в т.ч. не установлен драйвер) |
| query | упал запрос; ошибка сборки запроса (нет параметра, неизвестный тип); throw из callback `execStream`; обрыв fb-соединения; срабатывание вотчдога mssql |
| tx | не прошёл `BEGIN`/`COMMIT`; `COMMIT_TIMEOUT`; непредвиденный reject тела транзакции |
| user | собственное исключение callback транзакции (не `TDbError`) |
| timeout | истёк дедлайн транзакции или таймаут данных `execStream`/`exec` |
| aborted | сработал внешний `AbortSignal` |

## 5. Фасад `DbConnection` (`db/index.ts`)

```ts
class DbConnection {
  constructor(connection: TConnectionParam)
  exec(query: string, params: TDbParam[], options?: TExecOptions): Promise<TResult<TDbRes[], TDbError>>
  execStream(query: string, params: TDbParam[], callback: (e: TDbStreamEvent) => void, options?: TExecOptions): Promise<void>
  execTxDynamic<T = void>(cb: TDbTxCb<T>, options?: TTxOptions): Promise<TResult<T, TDbError>>
  /** @deprecated */ execTxDynamic<T = void>(cb: TDbTxCb<T>, timeoutMs?: number): Promise<TResult<T, TDbError>>
  ping(options?: TExecOptions): Promise<TResult<null, TDbError>>
  version(options?: TExecOptions): Promise<TResult<string, TDbError>>
  kind(): TDbKind
  title(): string   // dbTitle
  user(): string    // dbUser
  close(): Promise<void>
}
```

### 5.1. Ленивое создание адаптера

- Конструктор только валидирует (§3.5) и сохраняет конфиг; сети не касается.
- `_adapter()` кеширует **промис** адаптера (`_adapterPromise`); адаптер создаётся динамическим `import('./adapters/<kind>')` — драйвер грузится только для используемого `kind`. При ошибке создания кеш сбрасывается (следующий вызов попробует снова), ошибка отдаётся как `kind: 'connect'`. Неизвестный `kind` → `unsupported db kind: …`.
- Пулы внутри адаптеров тоже создаются лениво при первом запросе.
- `close()`: если адаптер не создавался — no-op; иначе `adapter.close()`. `_adapterPromise` не сбрасывается; адаптеры после `close()` лениво пересоздают пул (принятый долг, §9).

### 5.2. `execStream` — таймауты и гарантия `finish`

Константы по умолчанию: `FIRST_DATA_TIMEOUT_MS = NEXT_ROW_TIMEOUT_MS = 12 ч`. `0` в опции — «без таймаута».

Алгоритм:
1. `assertTimeoutMs` для обоих таймаутов (синхронный `TypeError`).
2. `signal` уже отменён → `finish{aborted}` и выход. Ошибка создания адаптера → `finish{connect}`.
3. Внутренний `AbortController` передаётся адаптеру. Один таймер: сначала взведён на `firstDataTimeoutMs`, после каждого нефинишного события перевзводится на `idleTimeoutMs` (`timer.refresh()` при неизменном окне). Срабатывание → `finishEarly(TDbError{kind:'timeout', code:'TIMEOUT'})` с человекочитаемым временем (`humanMs`: ms/s/min/h).
4. `finishEarly`: ровно один раз — гасит таймер, абортит адаптер, шлёт `finish` потребителю, и резолвит промис через `Promise.race([run, gaveUp])` — **вызов возвращает управление, даже если драйвер завис** и адаптер так и не завершился.
5. События после `settled` отбрасываются. Throw из callback потребителя на любом событии превращается в `finishEarly(toDbError(err, 'query'))` (решение 6 владельца: `query`, не `user`); throw из обработчика самого `finish` проглатывается.
6. Если адаптер завершился без `finish` — фасад досылает пустой `finish`. Reject адаптера → `finish{query}`.
7. В `finally` снимаются таймер и слушатель внешнего сигнала.

Инвариант: **ровно один `finish` на вызов и промис всегда резолвится, никогда не реджектится** (кроме синхронной валидации).

### 5.3. `exec`

Обёртка над `execStream`, собирающая `TDbRes[]`: событие `schema` открывает новый набор; `row` добавляется в текущий; `rowsAffected`/`outParams` пишутся в текущий набор (создавая его при отсутствии); `finish.error` → `{ok:false}`. Таймауты валидируются до `try` (наружу `TypeError`).

### 5.4. `ping` / `version`

- `ping` выполняет `adapter.pingQuery()` через `exec` и возвращает `{ok:true, result:null}`.
- `version` выполняет `versionQuery()`, берёт первое значение первой строки (`String(v)`); нет строки или `NULL` → `{kind:'query', code:'NO_VERSION'}`. При ошибке `kind:'query'` и наличии `versionFallbackQuery` (только ora) — выполняется запасной запрос; если и он упал — исходная ошибка с суффиксом `(fallback also failed: …)`.

| kind | pingQuery | versionQuery | fallback |
|---|---|---|---|
| mssql | `SELECT 1 AS p` | `SELECT @@VERSION AS ver` | — |
| pg | `SELECT 1 AS p` | `SELECT version() AS ver` | — |
| ora | `SELECT 1 AS p FROM dual` | `SELECT banner AS ver FROM v$version WHERE rownum = 1` | `SELECT version AS ver FROM PRODUCT_COMPONENT_VERSION WHERE rownum = 1` |
| fb | `SELECT 1 AS p FROM rdb$database` | `SELECT rdb$get_context('SYSTEM', 'ENGINE_VERSION') AS ver FROM rdb$database` | — |

### 5.5. `execTxDynamic`

Принимает `TTxOptions` (или устаревший голый `timeoutMs: number`). Валидация `timeoutMs`; уже отменённый `signal` → `aborted`; ошибка адаптера → `connect`; дальше — `adapter.execTxDynamic(cb, timeoutMs, signal)`.

Контракт для потребителя: `cb(exec, signal)` выполняет запросы через `exec`; успешное завершение `cb` → COMMIT и `{ok:true, result}`, любая ошибка → ROLLBACK и `{ok:false}`. Ошибка `TDbError` из `exec` возвращается как есть (`isDbError`), иное исключение `cb` → `kind:'user'`. После аборта `exec` реджектится, а результат `cb`, пришедший после аборта, игнорируется; COMMIT после аборта не выполняется.

Результат statement в транзакции — **один** набор строк (первый recordset, без `schema`); DML даёт `rowsAffected` (в т.ч. `0`); смешанный пакет DML+SELECT — только счётчик DML. Исключение — Oracle `implicitResults` (отдельные `{schema, rows}`).

## 6. Общие механизмы (`helpers.ts`, `placeholders.ts`)

### 6.1. Ошибки

- `toDbError(err, kind)`: `code` = первое непустое из `number` (mssql) → `gdscode` (fb) → `code` → `sqlState`, приводится к строке; `message` — `err.message` или `String(err)`; `stack` — из реального `Error` или строкового `stack`.
- `isDbError(err)`: объект с `message: string`, `kind` из шести литералов **и** `code != null || stack != null` (признак реального происхождения; эвристика принята, решение 7). Литералы `kind` продублированы вручную (решение 10).
- `abortError(reason)`: внутренний `TxTimeout` → `{timeout, TIMEOUT}`; `CommitTimeout` → `{tx, COMMIT_TIMEOUT, 'COMMIT outcome unknown'}`; иначе `{aborted, ABORTED}` с message/stack причины.

### 6.2. `withTxTimeout(timeoutMs, body, external?)`

Общий для четырёх адаптеров каркас дедлайна транзакции:
- нет дедлайна (`undefined`/`0`) и нет внешнего сигнала → просто `body`, reject → `kind:'tx'`;
- внешний сигнал уже отменён → `aborted` без вызова `body`;
- иначе `body(signal, armCommitDeadline)` гоняется с таймером дедлайна (→ abort `TxTimeout`, результат `{timeout, TIMEOUT}`) и внешним abort (→ `{aborted, ABORTED}`); первый исход побеждает, остальные игнорируются; таймер и слушатели снимаются.
- `armCommitDeadline()` вызывается адаптером непосредственно перед COMMIT: перевзводит таймер на **ещё один полный `timeoutMs`**, срабатывание которого даёт `{tx, COMMIT_TIMEOUT, 'COMMIT outcome unknown'}` (решение 2, вариант A). Исход неоднозначен — повтор обязан быть идемпотентным.

### 6.3. Плейсхолдеры `:name`

`mapPlaceholders(query, fn, to?, atom = SQL_ATOM)` — единый сканер одним глобальным регэкспом `atom | (?<!:):(?<ph>[A-Za-z_]\w*)`:
- «атомы» (`SQL_ATOM`): строки `'…'` (экранирование `''`, обратный слэш — обычный символ), quoted-идентификаторы `"…"`, `-- …`, `/* … */` — копируются байт-в-байт;
- `::` (каст pg / scope) — не плейсхолдер; имя начинается с буквы/`_`, поэтому `arr[1:2]` не трогается;
- `to` — граница: плейсхолдеры с позицией `>= to` не переписываются (для fb `EXECUTE BLOCK`);
- регэксп кешируется по `atom` (`scanCache`); `fn` не должна реентерабельно вызывать `mapPlaceholders` с тем же атомом.

Диалектные атомы:
- `SQL_ATOM_MSSQL` = `[...]` + `SQL_ATOM` (bracket-идентификатор `[a:b]` — один атом);
- `SQL_ATOM_PG` = `E'…'` (с backslash-экранированием) + dollar-quoting `$tag$…$tag$` / `$$…$$` + `SQL_ATOM`; квадратные скобки — код (`ARRAY[:a]`, `arr[:i]` подставляются);
- `SQL_ATOM_ORA` = q-quote `q'[…]'`, `q'{…}'`, `q'(…)'`, `q'<…>'`, `q'X…X'` (с префиксом `n`/`N`) + `SQL_ATOM`;
- `maskPgBlockComments(sql)` — предпроход для pg: вложенные `/* /* */ */` маскируются токеном `<sep><index><sep>`, где `sep` — первый управляющий символ, отсутствующий во входе (fallback `'\uE000'`, решение 8); после подстановки `restore()` возвращает комментарии. Незакрытый комментарий оставляется как есть.

Подстановка по диалектам:

| kind | `:name` → | Особенности |
|---|---|---|
| mssql | `@name` | отсутствующий параметр → `mssql: param not found: <name>` |
| pg | `$N` | повтор одного имени → тот же `$N` (дедуп); значения в порядке первого появления |
| ora | `:name` (нативно) | сопоставление имён без учёта регистра; дубликат имени в разном регистре → `ora: duplicate param (case-insensitive)`; в `CREATE [OR REPLACE] [EDITIONABLE\|NONEDITIONABLE] TRIGGER` `:new`/`:old` и алиасы из `REFERENCING` не считаются параметрами |
| fb | `?` | значения позиционно в порядке вхождения (повтор — повтор значения); для `EXECUTE BLOCK` обрабатывается только заголовок до первого `AS` вне скобок/литералов (`execBlockBodyAt`) |

Лишние (неиспользованные) параметры не ошибка. Ошибки сборки — до обращения к серверу и пулу.

## 7. Адаптеры

Общие требования ко всем: класс `*Adapter implements IDbAdapter`; конструктор валидирует `connectTimeout` (ora — ещё `assertOraPool`); `execStream` никогда не реджектит, а завершает `finish` (ошибки сборки/подключения — `finish{query|connect}`), throw из `finish`-обработчика потребителя проглатывается; поддержка `AbortSignal` в `execStream` и `execTxDynamic` с жёстким освобождением соединения; транзакция строится на `withTxTimeout`.

### 7.1. MSSQL (`mssql`)

- Один `sql.ConnectionPool` на адаптер, лениво (`pool()`), `connect()` идемпотентен; `pool.on('error', () => {})` гасит переэмит потери соединения. `close()` закрывает пул (ошибки игнорируются).
- Параметры: `assertMssqlParam` (отклоняет out/inout, проверяет тип) до `connect()`, затем `mssqlInput` (`request.input(name, value)` или `request.input(name, mssqlType(type), value)`); `mssqlType(name)` ищет фабрику в `sql.TYPES` (`DateTime2`, `NVarChar`, …), неизвестное имя → `mssql: unknown param type`.
- Схема: `toSchema(columns)` — `kind` = `column.type.name` (имя конструктора типа), `len`, `scale`, `precision`.
- `execStream`: `request.stream = true`; события `recordset` → `schema`, `row` → `row`, `rowsaffected` → (через `MssqlStatementTracker`) `schema: []` + `rowsAffected`; `error` завершает сразу (не ждать `done`); `done` → `finish`. Аборт: закрыть сырое соединение запроса (`request._currentRequest.connection.close()`), если его нет — `request.cancel()`; затем `finish{aborted}`.
- `MssqlStatementTracker` — различение SELECT/DML по порядку событий: `recordset` открывает SELECT; `rowsaffected` при открытом SELECT, равный числу выданных строк, — счётчик самого SELECT (отбрасывается), иначе — DML. Неразличим только случай SELECT под `SET NOCOUNT ON` + DML, изменивший ровно столько же строк (решается в пользу SELECT — принятый край).
- Транзакция: отдельный пул на транзакцию, `new sql.Transaction(pool)`, statement-ы — потоковые запросы с тем же трекером. **Вотчдог тишины**: окно перевзводится на каждое событие `recordset`/`row`/`rowsaffected`; при отсутствии событий и `done` дольше `timeoutMs` транзакции (или `MSSQL_TX_DONE_WATCHDOG_FALLBACK_MS = 15_000` без дедлайна — выровнено на дефолтный `requestTimeout`) соединение рвётся, statement завершается `kind:'query'`. Одиночный долгий молчащий statement (`WAITFOR DELAY`) под вотчдог попадает — принято (решение 4).

### 7.2. PostgreSQL (`pg`)

- `pg.Pool` на адаптер (лениво); SSL — см. §3.2.
- Параметризованный запрос стримится через `pg.Query` (событие `'row'`); запрос **без параметров** идёт простым протоколом (поддерживает мульти-statement, но буферизует результат в памяти) — задокументированное поведение.
- Схема: `toSchema(fields)` с картой OID → имя типа `PG_TYPE_NAME`.
- `rowsAffected` — только для команд из белого списка `DML_COMMANDS = {INSERT, UPDATE, DELETE, MERGE}` (FETCH/COPY/CREATE TABLE AS не дают ложного счётчика; `INSERT … RETURNING` даёт реальный).
- Аборт: бэкенд не замечает пропажу клиента, поэтому отмена — отдельным клиентом (`connectionTimeoutMillis: 30_000`, `query_timeout: 30_000`) запросом `SELECT pg_cancel_backend($1)` по `processID`; требует ту же роль и свободный слот.
- Транзакция: клиент из пула, `BEGIN` → statement-ы → `COMMIT`/`ROLLBACK`.

### 7.3. Oracle (`oracledb`)

- Пул `oracledb.createPool` (`connectString`, `privilege` через карту в константы драйвера, `connectTimeout` в секундах, `poolMin/Max/Increment`, `queueTimeout`). Привилегированный вход — только Thin.
- Маршрутизация: `isRowQuery(sql)` — пропуск пробелов, `--`/`/* */` комментариев и открывающих `(`, затем `^(select|with)\b`. Строковые запросы — `conn.queryStream()` с `OUT_FORMAT_OBJECT`; DML/PL/SQL — `conn.execute()` (autoCommit), с выдачей `rowsAffected`, `outParams` (`outBinds`) и `implicitResults`.
- Bind: `oraBind(p)` — `BIND_IN/OUT/INOUT`; без `type` IN отдаёт голое значение, OUT/INOUT → ошибка `ora: <dir> parameter <name> needs a type` (иначе драйвер ответит `NJS-0058`). Тип — из `ORA_IN_TYPES`: `VARCHAR2, NVARCHAR2, CHAR, NUMBER, DATE, TIMESTAMP, CLOB, BLOB, RAW, BOOLEAN, JSON` → `oracledb.DB_TYPE_*`; иное → `ora: unknown param type`. Для OUT `val: undefined`.
- Схема: `toSchema(metaData)` — `name`, `kind = dbTypeName`, `len = byteSize`, `scale`, `precision`.
- `implicitResults` (`DBMS_SQL.RETURN_RESULT`): каждый ResultSet читается и **обязательно закрывается** (`readImplicitResults`), отдаётся как отдельный `{schema, rows}`.
- Освобождение соединения: всегда в `finally`; перед `close()` дождаться (`boundedWait`, `ORA_CLOSE_WAIT_FALLBACK_MS = 1000`, таймер снимается) закрытия стрима (`'close'` после `'end'`), DML-обработчика и interrupt — иначе `NJS-032` и соединение выпадает из пула. Неудачный `close()` → `close({ drop: true })` (решение 3: молчаливая потеря сессии дешевле утечки слота).
- Аборт: `conn.break()` **только если на соединении реально выполняется операция** (`operationsInFlight > 0`), иначе сессия останется отменённой и следующий statement получит `ORA-01013`.
- Транзакция: `execute(..., { autoCommit: false, outFormat: OUT_FORMAT_OBJECT, resultSet: true })`; ResultSet читается `getRows()` и закрывается в `finally`; учёт летящих операций — счётчик `operationsInFlight` + `Set` never-rejecting зеркал `inFlightExecs` (решение 9); COMMIT тоже считается операцией и зеркалится. Аборт → `teardown` (break при необходимости + `release`); при уже отменённом сигнале после `getConnection()` — `release()` без break. Rollback при ошибке `cb`/COMMIT — только если сигнал не отменён (иначе гонка с `close()` teardown-а). Перед COMMIT — `armCommitDeadline()`.

### 7.4. Firebird (`node-firebird@2.19.1`)

- Стримингового API у драйвера нет: адаптер использует низкоуровневый wire-API (`Transaction`/`Statement`, `newStatement`, `parseRecordCounts` из `node-firebird/lib/wire/*`) — один подготовленный statement даёт схему (из describe, в т.ч. для пустого результата), строки и счётчик (`isc_info_sql_records`).
- Схема: `fbSchema(output)` — `name = alias ?? field`, `kind` из обратной карты `Firebird.SQL_TYPES` (`FB_TYPE_NAME`, без префикса `SQL_`/`SQL_TYPE_`), `len = nativeLength ?? length`, `scale`.
- Пула нет: новый attach на каждый запрос/транзакцию, ограниченный `connectTimeout` и `signal`; по окончании — detach / `dropConnection` (жёсткий разрыв сокета).
- Потеря соединения (`watchConnection`): события драйвера `error`/`reconnect` и закрытие сокета → `{kind:'query', code:'FB_CONN_LOST', message:'fb: connection lost…'}`; самопереподключение драйвера отменяется.
- Двоичные BLOB (`SUB_TYPE 0`) не поддерживаются; текстовые — как строки.
- **Monkey-patch**: при импорте модуля `Connection.prototype.attach` оборачивается — на ошибке attach выставляется `_isDetach = true`, гасится `_retry_connection_id`, `_socket.destroy()` (драйвер иначе течёт сокетом → EMFILE и незавершающиеся процессы). Защита от повторного применения — флаг `__vvPatched`. Живой `exports.connection` читается через `createRequire` (`fbLive`). Версия драйвера пинуется точно из-за опоры на внутренности.

## 8. Решения владельца (требования)

1. `typescript ^7.0.2` — оставить.
2. COMMIT_TIMEOUT — отдельный таймер на фазу commit длительностью `timeoutMs`, исход неоднозначен (§6.2).
3. Oracle `close({drop:true})` при неудачном close — без логирования/метрик (в библиотеке нет канала логов).
4. Окно вотчдога mssql = `timeoutMs` транзакции, без дедлайна — 15 000 мс.
5. Throw из callback `execStream` → `kind:'query'`.
6. Двойная валидация (параметры mssql, таймауты, `connectTimeout` в фасаде и адаптерах) — осознанная; `exec` валидирует до `try`, `execStream` — так, чтобы закончиться `finish`, mssql — до `connect()`.
7. `isDbError` — эвристика `code != null || stack != null`.
8. Fallback-разделитель `'\uE000'` в `maskPgBlockComments` — только для вырожденного входа.
9. Oracle `inFlightExecs` — `Set` never-rejecting зеркал.
10. Литералы `kind` в `isDbError` дублируются вручную (без общего const-массива — избежать цикла импорта).
11. Приватный `OraAdapter._connParams()` может иметь неявный тип.
12. Abort во время fb attach может отдаваться как `connect` вместо `aborted` — неважно, гонку уже выиграл abort.
13. Упавший statement в mssql-транзакции покрывается юнит-тестом с моком, без живого теста.
14. Адаптер напрямую не обязан сдерживать throw из не-`finish` событий — это делает фасад.

## 9. Ограничения и принятый долг (открытые пункты)

1. `rowsAffected` для mssql `OUTPUT` / fb `RETURNING` не поддерживается — требует распознавания в SQL.
2. mssql: аборт до захвата соединения — `request.cancel()` может не сработать (приватный API).
3. fb: monkey-patch `attach`, глобальный `exports.connection`, точный пин драйвера, deep-import-ы без расширений, attach + разрыв сокета на каждый запрос.
4. mssql: опора на приватные `_currentRequest`/`_acquiredConnection`; отдельный пул на транзакцию.
5. pg: опора на `processID`/`connection.stream`; новое соединение на каждый abort (`_cancelBackend`).
6. ora: `close(0)` пула обрывает чужие активные соединения.
7. TLS-дефолты нестрогие (`encrypt=false`, `rejectUnauthorized:false`).
8. fb: потеря соединения во время летящего COMMIT — завершение полагается на драйвер; без дедлайна жёсткой границы нет.
9. Гонка `DbConnection.close()` / `execStream`: `_adapterPromise` не сбрасывается, пул пересоздаётся лениво — допустимо.
10. pg без параметров буферизует весь результат (простой протокол).

При обновлении любого драйвера — перепроверка опор на внутренности (п. 2–6), для fb — воспроизведение утечки сокета при неудачном attach.
