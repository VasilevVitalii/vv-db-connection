# Принятые решения владельца (сознательные — НЕ переоткрывать как ошибки)

## Из старого цикла (перенесено из `ai/.agreed.md`, review1–review28)

1. **`typescript: ^7.0.2` — оставить.** Решено в review4 как «не баг», подтверждено (B1). Будущие ревью не поднимают пункт без новой информации.

2. **COMMIT_TIMEOUT — вариант A** : отдельный «жёсткий» таймер на фазу commit той же длительности (`timeoutMs`); при срабатывании даёт неоднозначный исход `{ ok:false, error:{ message:'COMMIT outcome unknown', kind:'tx', code:'COMMIT_TIMEOUT' } }`. Исход неоднозначен (commit мог уже пройти) — повтор после `COMMIT_TIMEOUT` обязан быть идемпотентным. (Рекомендация архитектора была (б) — задокументировать; владелец выбрал (a).)

3. **ora `drop: true`**: молча пересоздаёт сессию, теряя незакоммиченную работу; канала логирования/метрик в библиотеке нет. Осознанное решение: потеря сессии дешевле утёкшего слота пула; добавлять лог/метрики в библиотеку не будем.

4. **окно вотчдога mssql** : окно = `timeoutMs` транзакции; для голого `execTxDynamic` без дедлайна — константа `15_000`, выровненная на дефолтный `requestTimeout` mssql/tedious. Остаточная неоднозначность принята: одиночный statement, молчащий дольше окна (напр. `WAITFOR DELAY`), неотличим от зависания без дедлайна и будет убит вотчдогом.

5. **throw из пользовательского callback в `execStream`**: маркируется `kind: 'query'` (баг обработчика читается как retryable query-failure). Оставить как есть (не `user`) — задокументировано в README:107.

6. **двойная валидация mssql**: params `assertMssqlParam` на 128 и в `mssqlInput`; таймауты `exec`/`execStream`; `connectTimeout` в `DbConnection` и конструкторах адаптеров — осознанный дубль. `exec` валидирует до `try` (`TypeError` наружу), `execStream` — чтобы не отклонить promise вместо `finish`; mssql валидирует до `connect()`, чтобы не занимать слот пула. Удаление любого слоя вводит регрессию контракта.

7. **`isDbError`**: классифицировать как DB-ошибку только при реальном признаке (код драйвера `code`/`number`/`gdscode`/`sqlState`, свёрнутый в `code`, или `stack` от реального `Error`), а не одного `kind`. Валидация параметров без кода несёт `stack`. Эвристика `code != null || stack != null` оставлена (172 теста зелёные; brand-symbol ломает синтетические `TDbError` без `code`/`stack`).

8. **placeholders fallback `'\uE000'`**: выбирается только если во входном SQL присутствуют все 29 управляющих символов (вырожденный, невалидный SQL). Риск практически нулевой; задокументирован в коде.

9. **ora `inFlightExecs` — Set never-rejecting зеркал**: Set, а не долг и не одиночный `inFlightExec`; симметрично счётчику и убирает хак сброса по `=== 0`.

10. **`fb.ts:419-421` abort attach → `toDbError(err,'connect')` теряет kind `aborted`→`connect`**: принято без кода — ошибка мёртвая, до потребителя не доходит (гонку `withTxTimeout` к этому моменту уже выиграл abort), чинить нечего — нет потребителя.

11. **живой интеграционный тест упавшего statement в tx**: покрыт юнит-тестом с моком, эмитящим `error` + reject до `'done'`. Живой тест против MSSQL не добавляем.

12. **тесты throw из `row`/`schema`/`data` на прямом `IDbAdapter`**: не нужны — после сужения контракта адаптер не обещает сдерживать не-finish throw.

13. scan-20261107-0001.md. `version()` при срабатывании fallback-запроса не вычитает уже потраченное время: у fallback свой бюджет `firstDataTimeoutMs`/`idleTimeoutMs`, суммарно вызов может занять до двух заданных дедлайнов (вариант (а) — задокументировано в README, время не вычитаем).
